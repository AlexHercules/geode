# 产品分层：本地软件 × 平台

## 原则

本地软件（Borges 写作端）**免费且开源**；平台（花园）闭源运营。二者深度绑定，但绑定靠**网络效应和服务**，不靠数据劫持——书稿格式是开放标准，作者随时能带走自己的仓库。带不走的是读者、故事树和分成，这才是健康的护城河。

参照系：VS Code（MIT 开源）+ GitHub/Copilot（闭源服务）、Obsidian（本地免费 + Sync/Publish 付费）、GitLab CE/EE 开核模式。共同点：**本地工具负责赢得信任和占有工作流，云端服务负责变现**。

## 职责切分

| | 本地：Borges 写作端（开源） | 平台：花园（闭源服务） |
|---|---|---|
| 写作流水线 | ✅ 全部工位本地可跑（自带 API key 时完全离线于平台） | 托管版流水线（订阅者无需配模型） |
| Gate | ✅ 确定性 gate 全部开源（schema/Vale 规则/纠错） | **发布时服务端复验**——本地 gate 是开发体验，服务端 gate 是发布资格，防止改造客户端绕过 |
| canon pack / 书稿 | ✅ 开放格式（git 仓库 + 公开 schema），本地即全量 | canon registry：全网故事树索引、分岔点发现、跨树搜索 |
| 故事树 | 单仓库内的分支 | **全局树**：跨作者的分支拓扑、阅读路径、热度数据 |
| 身份与归属 | git commit 签名 | 账号体系 + 签名校验：发布的每章绑定平台身份，归属即权证 |
| 分成 | — | **结算系统**：阅读计量、广告收入、沿链瀑布分账（charter 执行） |
| 读者 | — | 阅读端、推荐、广告、续写入口 |
| 模型调用 | 自带 key（BYOK）免费 | 模型网关：平台代理调用 = 订阅收入（第二曲线） |

## 五个绑定点（为什么本地用户会连平台）

1. **发布**：本地写完的书要被人读到，只有发布到花园这一条路有读者和分成；
2. **续写入口**：你的书想被分岔（= 想长成树 = 想拿世界观税），必须在平台上让读者点到"从这里续写"；
3. **分成结算**：charter 的执行需要可信第三方计量阅读和分账，本地软件做不了；
4. **托管流水线**：不会配 API key 的大众用户直接用平台额度（免费档 + 订阅）；
5. **registry**：找热门树、找好分岔点、看自己分支的传播图谱——数据只在云端。

注意第 1、2 点的方向性：**不是平台锁住作者，是作者需要平台的读者**。这和 Obsidian 用户买 Sync 是同构的——本体免费好用建立信任，付费/绑定发生在"协作与分发"这个本地天然做不到的层。

## 开源协议选择

风险场景：竞争对手 fork 开源写作端，接上自己的平台，搭竞品花园。

| 选项 | 取舍 |
|---|---|
| MIT/Apache | 最大化采用，但对上述场景零防御 |
| **AGPL-3.0**（推荐） | 真开源（OSI 认证），传染性覆盖网络服务：竞品基于它建 SaaS 必须开源其改动。Grafana 同款。对个人用户和贡献者无任何负担 |
| BSL / FSL（Sentry 式） | 防御最强（禁止竞争性用途，2-4 年后转开源），但**不是开源**，损失"开源写作工具"的社区号召力 |
| ELv2 | 介于两者之间，同样非 OSI |

**建议：写作端核心 AGPL-3.0；book repo 格式与 canon schema 用 CC0/MIT 单独发布**（格式越开放，生态越大，对平台越有利——格式是标准不是产品）。平台侧代码不开源，无协议问题。

另一道防线比协议更硬：**服务端 gate 复验 + 身份签名 + 结算系统在平台**。竞品抄得走客户端，抄不走读者网络和信任的分账系统。协议只是减速带，网络效应才是墙。

## 形态路线

1. **阶段 0–1**：本地端 = CLI（StoryCraftr 形态），跑在书稿 git 仓库上，gate 即命令；
2. **阶段 2**：桌面端（CLI 内核 + GUI 壳），「发布到花园」按钮出现，账号体系上线；
3. **阶段 3**：平台 Web 阅读端 + 续写按钮调用的就是同一套开源流水线的托管版——**本地端和云端跑同一份开源 harness 代码**，保证"本地能复现平台的 gate 结果"，这是开源端最大的诚意，也是格式可信的来源。
